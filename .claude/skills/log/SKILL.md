# log

세션이 바뀌면 맥락이 사라진다. **기록이 없으면 같은 조사를 반복한다.**
이 스킬은 알아낸 것을 올바른 문서에 올바른 형태로 넣는다.

## 어디에 쓸지 고른다

| 쓸 내용 | 문서 |
| --- | --- |
| 지금 어디까지 왔는지, 다음에 뭘 할지 | `Editor/Docs/status.md` |
| 게임 코드·실험에서 **알아낸 사실** | `Editor/Docs/research.md` |
| 시도했으나 **안 된 것과 그 이유** | `Editor/Docs/failures.md` (없으면 만든다) |
| 기획 **결정이 바뀜** | `Editor/Docs/design.md` — 승인 후에만 |
| 일하는 **절차가 바뀜** | `Editor/Docs/workflow.md` |

하나의 작업이 여러 문서를 건드리는 게 정상이다. 예: 원인을 규명해 고쳤다면
→ 사실은 `research.md`, 진행 상태는 `status.md`, 헛짚은 접근은 `failures.md`.

## status.md

**가장 자주 갱신한다. 작업이 끝날 때마다.**
기준: **세션을 새로 시작한 사람이 이 문서만 읽고 이어갈 수 있어야 한다.**

- 맨 위 `최종 갱신:` 줄에 날짜와 한 줄 요약. 날짜는 추측하지 말고 확인한다
- `## 현재 상태` 를 새로 쓴다. 이전 내용은 지우지 말고 `_(아래는 이전 단계 기록)_`
  아래로 밀어 넣는다
- **코드 완료와 검증 완료를 구분해서 적는다.** 인게임 확인을 안 했으면 그렇게 쓴다
- 다음에 할 일은 **행동**으로 쓴다. "파일런 작업" ✗ → "파일런 좌표 조건으로 보호 범위를 좁힌다" ○
- 체크박스를 채운다

## research.md

디컴파일·실험으로 알아낸 **사실**만. 계획이나 의견은 안 쓴다.

- 클래스·컴포넌트·시스템 이름을 정확히 적는다. 나중에 grep으로 찾을 수 있어야 한다
- **어떻게 알아냈는지**를 함께 적는다 (디컴파일한 클래스, 실행한 실험, 본 로그)
- 기획서의 `확인 필요` 항목이 해결되면 여기에 근거를 남기고 `design.md` 를 갱신한다
- 사실이 뒤집히면 지우지 말고 **왜 틀렸는지와 함께** 고쳐 쓴다

## failures.md

**성공보다 중요하다.** 남기지 않으면 같은 시도를 반복한다.

항목마다: 무엇을 시도했나 / 무슨 일이 벌어졌나 / **왜 안 됐나** / 대신 무엇을 했나.
원인을 모르면 "원인 불명"이라고 쓴다. 지어내지 않는다.

## 쓰는 방식

- **한글 본문.** 파일명만 ASCII다
- 사실과 추측을 섞지 않는다. 추측에는 `추정`, 미검증에는 `미검증`을 붙인다
- 이미 있는 내용을 다시 쓰지 않는다. 갱신할 곳을 먼저 찾는다
- 코드에서 확인 가능한 것(함수 시그니처 등)은 문서에 복제하지 말고 파일 경로를 가리킨다
- 문서만 고치는 것은 코드 변경이 아니지만, **여전히 파일 수정이다** — `CLAUDE.md` §0에
  따라 플랜 승인이 필요하다. 사람이 "기록해줘"라고 한 경우가 곧 그 지시다
