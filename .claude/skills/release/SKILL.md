# release

`main`에 누적된 변경을 **태그 + GitHub 릴리스**로 기록한다.

## release ≠ deploy

| | release | deploy |
| --- | --- | --- |
| 하는 일 | 태그 + GitHub 릴리스 + 노트 | mod.io / 스팀 창작마당 업로드 |
| 대상 | 기록 | 실제 사용자 |
| 되돌리기 | 가능 (지우고 다시 찍으면 됨) | 사실상 불가능 |
| 실행 | **이 스킬** | **사람** |

**이 스킬은 GitHub 릴리스에서 멈춘다.** mod.io·창작마당 업로드는 절대 하지 않는다.
"릴리스 해줘"가 배포까지 실행되면 사고다.

---

## 1. 전제 확인

```bash
git branch --show-current              # main 이어야 한다
git status --porcelain                 # 비어 있어야 한다
git fetch origin && git status -sb     # 원격과 동기화됐는지
git tag -l 'v*' --sort=-v:refname | head -3
```

`main`이 아니거나, 커밋되지 않은 변경이 있거나, 원격과 어긋나 있으면 **중단하고 알린다.**

`git tag`에 `-l 'v*'` 필터가 **반드시** 붙어야 한다. 저장소에는 버전이 아닌 태그가 있을 수
있고, 필터 없이 정렬하면 그런 태그가 "직전 릴리스"로 잡혀 노트 범위가 통째로 틀어진다.

## 2. 노트 초안

```bash
git log --no-merges <직전태그>..HEAD --format='%s%n%b%n---'
```

태그가 하나도 없으면 저장소 처음부터 훑는다.

`--no-merges`가 필요한 이유: 머지 방식이 merge commit이라 PR마다 `Merge pull request #N
from …` 이 하나씩 쌓인다. 사용자에게 아무 의미도 없고 실제 내용은 개별 커밋에 있다.

노트 작성 규칙:

- 커밋 subject를 기반으로 하되 나열이 아니라 사용자 관점으로 묶는다
- `feat:` → 새 기능, `fix:` → 고친 것, `chore:`/`docs:` → 묶어서 한 줄 이하
- **검증되지 않은 것은 그렇게 적는다.** 이 프로젝트는 코드 완료와 검증 완료를 구분한다
- 알려진 한계가 있으면 반드시 적는다 (예: 특정 폭탄류가 보호를 우회할 수 있음)
- **노트는 영문으로 쓴다** (`CLAUDE.md` §1-1). 릴리스 페이지는 이 저장소에서 외부 노출이
  가장 큰 산출물이다

## 3. 릴리스 판단 — 찍을지부터 정한다

**버전 번호를 고르기 전에 이걸 먼저 묻는다.**

> 이 빌드를 설치한 사람의 게임이 나아지는가?

판단 재료는 2단계에서 **직접 쓴 노트**다. "Not done yet" 항목이 기능 항목을 압도하면
답은 아니오다. 커밋이 많다는 건 근거가 아니다 — 도구·문서 커밋 20개는 사용자에게 아무것도
아니다.

**세 갈래를 전부 제시하고 사람이 고르게 한다. 임의로 찍지도, 임의로 멈추지도 않는다.**

| 상태 | 선택 |
| --- | --- |
| 남에게 설치를 권할 수 있다 | 정식 릴리스 |
| 기록은 남기되 설치는 권하지 않는다 | **`--prerelease`** |
| 사용자에게 알릴 게 없다 | **찍지 않는다.** 이유를 설명하고 여기서 멈춘다 |

세 번째가 정답인 경우가 실제로 있다. 스킬이 호출됐다는 이유만으로 태그를 만들지 않는다.

### 버전 — "찍는다"를 고른 뒤에만

`Editor/Docs/workflow.md` §5 기준.

- **`0.1.0` = 처음으로 남에게 설치를 권할 수 있는 상태.** 그 전은 `0.0.x` + `--prerelease`다.
  **어느 개발 단계가 여기 해당하는지는 미리 정해두지 않는다** — 위 게이트로 그때 판단한다.
  기획서에도 단계별 버전은 정의돼 있지 않다
- **검증된** 기능이 늘면 마이너를 올린다 (`0.2.0`)
- 버그 수정만이면 패치 (`0.1.1`)
- 사용자에게 배포할 만한 상태가 되면 `1.0.0`

제안하고 **사용자 확인을 받는다.** 임의로 정하지 않는다.

### `--generate-notes` 는 쓰지 않는다 (결정 기록)

`gh release create --generate-notes`는 머지된 PR 목록으로 노트를 자동 생성한다. 형식은
우리 PR 제목과 잘 맞는다. 그런데도 쓰지 않는 이유:

- 이 프로젝트의 노트에는 **"검증됐는지"와 "아직 안 된 것"**이라는 판단이 들어가야 한다.
  자동 생성은 그 판단을 못 한다
- 위 3단계 게이트가 무력화된다. 노트가 자동으로 나오면 "찍을지"를 되묻지 않게 된다

초안 재료로 참고하는 것은 괜찮다. 하지만 **최종 노트는 직접 쓴다.**

## 4. 릴리스 생성

노트를 임시 파일에 쓰고 `--notes-file`로 넘긴다. 긴 노트를 `--notes "$(...)"`로 넘기면
따옴표·백틱에서 깨진다. **저장소 안에 임시 파일을 만들지 않는다** — 루트가 곧 modPath다.

```bash
NOTES="$(mktemp -t nbz-release)"
# ... 2단계에서 쓴 노트를 $NOTES 에 쓴다 ...
gh release create "v<버전>" --title "v<버전>" --notes-file "$NOTES"
rm -f "$NOTES"
```

3단계에서 "기록만"을 골랐으면 `--prerelease` 를 붙인다.

## 5. 멈추고 보고

- 릴리스 URL과 태그
- 포함된 커밋 수 / PR
- **배포는 사람이 한다**는 것을 다시 알린다. 배포를 원하면 무엇이 필요한지 정리해 주되
  업로드는 하지 않는다

---

## 잘못 찍었을 때

깃허브 릴리스는 기록이라 되돌릴 수 있다.

```bash
gh release delete v<버전> --yes
git push --delete origin v<버전>
git tag -d v<버전>
```

지우고 다시 찍으면 된다. 다만 **이미 배포(deploy)된 버전의 태그는 지우지 않는다** —
어떤 코드가 배포됐는지 추적할 수 없게 된다.
