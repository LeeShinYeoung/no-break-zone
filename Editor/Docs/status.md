### 레시피가 유일한 차단점이었다 (2026-08-06)

**빌드도 로드도 성공한다.** 인게임에서 막힌 것은 딱 하나 — 철 작업대 제작창에 우리 작업대
레시피가 안 떴다. 그리고 그게 모드의 유일한 문이라 **그 뒤 전부에 손이 닿지 않았다.**

원인은 우리 코드가 아니라 제작 UI 구조였다.

- **철 작업대는 18/18로 꽉 차 있다.** 제작창은 창 3개 × 6칸이라 벤치당 18개가 상한이다
- **게다가 화살표가 있다.** 기본·구리·주석 작업대를 흡수해서 목록이 구역으로 쪼개져 있고,
  UI는 선택된 구역만 그린다. 목록 끝(72번)에 붙인 우리 레시피는 **어느 구역에도 안 들어간다**

→ **자동화 테이블로 옮겼다** (6/18, 화살표 없음, 레퍼런스 모드 2건이 같은 벤치를 쓴다).
결정 근거는 `design.md` §4의 결정 기록, UI 구조와 벤치별 실측은 `research.md` 18장.

### 6단계 이후 보강 — 다중 타일 보호 (2026-08-05)

**기획서 §6의 규칙 하나가 구현이 안 된 채로 6단계까지 와 있었다.** 보호 판정이 오브젝트의
**원점 타일 하나만** 봤다. 2단계에 만든 `CoversRect`는 테스트까지 붙은 채 **한 번도 호출되지
않았다.**

- 1×1은 결과가 같아서 드러나지 않았다. 우리 작업대(2×1)부터 해당된다
- 판정을 **합집합**으로 정했다 — 타일마다 따로 보고, 각 타일이 어느 파일런이든 하나에 덮이면 된다
  (`research.md` 16장). 두 파일런 이음매에 걸친 물건도 보호된다
- **거는 쪽과 푸는 쪽이 같은 메서드를 부른다.** 어긋나면 보호는 걸리는데 영영 안 풀리는
  오브젝트가 생긴다
- `CoversRect`는 지웠다. 진짜 규칙이 둘로 보이는 게 애초의 사고 원인이었다

### 7단계에서 한 것 (코드 완료·미검증)

**설정 — 완료.** design.md §10의 네 항목이 `API.Config`로 등록된다 (`Scripts/NoBreakZoneConfig.cs`).
**`Conf/` 폴더는 만들 필요가 없었다** — 게임이 파일을 관리한다.

- 지름을 바꾸면 **재판정이 돈다.** 안 그러면 파일런을 껐다 켤 때까지 반영이 안 된다
- **"몹 피해 차단"에 새 메커니즘이 필요 없었다.** `IndestructibleCD`(플레이어발)와
  `DontDestroyOnZeroHealthCD`(모든 피해원)가 원래 다른 경로를 막고 있었다. 끄면 후자를 안 붙인다
- 등록 실패 시 상수 폴백. 설정 하나 때문에 보호가 죽지 않게

**현지화 — 구조만.** `Localization/` 폴더는 필요 없었다. **TextDataBlock이 곧 현지화**이고
`.csv`는 에디터 임포트용이다 (`research.md` 17장). 13개 슬롯 구조는 3단계부터 맞아 있었다.

⚠️ **한국어는 윈도우가 있어야 켜진다.** 13개 슬롯 중 어느 것이 한국어인지 모른다 —
주소가 게임 번들 안 에셋을 가리켜 레퍼런스 어디에도 없다. **한국어 문안은 이미 다 써뒀고**,
`genassets.py`의 `LANGUAGE_SLOTS`에 인덱스 하나만 적으면 켜진다. 배선은 임시로 켜서 확인함.

**배포 — 점검 목록만.** `Editor/Docs/deploy.md`. 업로드 절차 자체가 SDK 에디터 UI를 거쳐서
윈도우에서만 확인된다. `workflow.md` 6장의 빈칸이 그대로 남아 있다.

1단계 핵심 해결: 클라이언트 예측 오작동이 원인이었고, 게임 자체 플래그 `IndestructibleCD`를
서버+클라 양쪽 월드에서 켜서 해결. 상세·교훈은 `research.md` 9장.

2단계에서 한 것:

- `Scripts/`를 `Logic/`(게임 타입 비의존) · `Components/` · `Systems/`로 나눔
- 보호 범위를 21×21 정사각형 안으로 좁힘. **파일런 좌표는 아직 하드코딩** (3단계에서 대체)
- 태그 두 개 도입 — `NoBreakZoneEvaluatedCD`(매 프레임 월드 훑기 방지),
  `NoBreakZoneProtectedCD`(원래 무적이던 오브젝트를 4단계에서 잘못 되돌리지 않기 위해)
- `Editor/Tests/` — 범위 판정 + 보호 판별. 후자는 `object_flags.csv` 2282개 전수 회귀(569개 보호)
- `Editor/preflight.py` — 맥에서 돌리는 정적 검증 (아래)

### 이번 세션의 가장 큰 소득 — 조사에 윈도우가 필요 없어졌다

게임 전체 디컴파일 소스·공식 문서·최신 레퍼런스 모드가 전부 공개 저장소에 있다.
**게임 DLL 복사도, 디컴파일러 설치도 불필요.** 목록과 검증 근거는 `research.md` 10장.

그리고 **유니티 없이 프리팹을 쓸 수 있다는 것**을 실증했다 — `m_Script` fileID가 클래스
이름에서 계산된다(레퍼런스 184건 100% 일치). 레시피는 `research.md` 11장,
참조표는 `GameData/script_fileids.csv`.

윈도우에 남는 일은 **빌드와 인게임 검증** 둘뿐이다.

3단계에서 한 것:

- **`Editor/genassets.py`** — 에셋 생성기. 파일런 에셋 9종(프리팹 2, SpriteAsset, TextDataBlock,
  텍스처+임포트, 매니페스트, `.meta`들)을 스펙에서 찍는다. YAML을 손으로 안 쓴다.
  6단계의 렌즈·리모콘·작업대는 `SPECS` 리스트에 항목을 더하면 된다
- **guid·fileID·`m_address`를 전부 에셋 경로에서 해시로 유도한다.** 재실행해도 안 바뀌므로
  `--check`가 통과한다. 참조가 끊기는 사고(CLAUDE.md §1-2)를 구조적으로 막는다
- `Scripts/Systems/NoBreakZonePylonRegistrySystem.cs` — 실제 설치된 파일런을 찾아 좌표를 공급.
  `NoBreakZoneProtectionSystem`의 하드코딩 좌표가 사라졌다
- 파일런을 놓으면 **이미 판정이 끝난 오브젝트를 다시 판정한다.** 안 그러면 나중에 놓은 파일런이
  원래 있던 상자를 보호하지 못한다

6단계에서 앞당겨 온 것 — **파일런 작업대** (윈도우 접근이 막혀 있어 검증 없이 갈 수 있는 일을
밀어둔 것):

- `Scripts/Converters/NoBreakZoneWorkbenchRecipeInjectionConverter.cs` — 바닐라 작업대에 레시피 주입
  (대상은 2026-08-06에 철 작업대 → 자동화 테이블로 교체).
  **이게 없으면 모드가 인게임에서 도달 불가능하다**
- `Scripts/Graphics/NoBreakZoneWorkbenchGraphics.cs` — `CraftingBuilding` 파생. 내용은 비어 있고,
  프리팹이 루트 컴포넌트를 지목하는 형태를 확정시키는 것이 존재 이유다 (`research.md` 12장)
- `Scripts/NoBreakZoneObjectNames.cs` — 세이브에 박히는 오브젝트 이름을 한곳에 모음
- `m_address`가 **그 에셋의 Unity guid**임을 규명. 미검증 가정이 사라졌고 `preflight.py`가 검사한다

### 맥에서 돌리는 검증

```
python3 Editor/preflight.py         # 프리팹 참조·금지 네임스페이스·.meta 짝·asmdef·m_address
python3 Editor/genassets.py --check # 생성된 에셋이 스펙과 일치하는지
```

프리팹 `m_Script` 역산 · 금지 네임스페이스 · `.meta` 짝 · asmdef 참조를 본다.
**컴파일 검증이 아니다** — 타입 오류는 윈도우 빌드에서만 드러난다.

## 다음에 할 일

### 📍 체크포인트 1 — 사람이 윈도우에서 확인 (다음 작업)

**5단계 이후가 전부 이 위에 쌓인다.** 3·4단계와 앞당긴 작업대까지 한 번에 확인한다.

⚠️ **아래 목록의 상태는 "미검증"이 아니라 "미도달"이다.** 빌드와 로드는 성공하지만 작업대
레시피가 제작창에 안 떠서, 작업대를 만들 수 없고 그러면 파일런·렌즈·리모콘에 **손이 닿지 않는다.**
2번이 풀리면 나머지 37개가 한 번에 열린다.

```
유니티 에디터 닫기 → powershell -File Editor/build.ps1   → 종료 코드 0
유니티 Test Runner → NoBreakZone.Tests
게임 재시작 → Player.log 에서 [NoBreakZone] loaded
```

인게임에서 볼 것, 중요한 순서대로:

1. **자원 복제가 없는가** — 드릴로 광석이 정상 고갈, 곡괭이로 벽·광석 정상 채굴, 작물 수확 정상.
   기획서 §6이 다른 무엇보다 우선한다고 못박은 항목이다
2. **자동화 테이블(AutomationTable)에 `Pylon Workbench` 레시피가 뜨는가** ← **여기가 막혀 있던 곳.**
   재료는 철 주괴 12 + 나무 20 + 기계부품 1.
   **바닐라 레시피 6개(컨베이어·분배기·조잡한 드릴·드릴·로봇 팔·스프링클러)도 그대로 있어야 한다** —
   사라졌으면 카테고리를 만들고 있는 것이다.
   안 뜨면 `Player.log`의 `[NoBreakZone] AutomationTable prefab` 줄을 본다 (slots·ours·categories·empty)
3. **작업대를 설치하고 E로 열리는가** ← **UnityEvent 배선이 여기서 드러난다.**
   `m_TargetAssemblyTypeName` 문자열은 `preflight.py`가 못 잡는다. 4번(파일런 E키)도 같은 배선이라
   둘 다 안 되면 원인은 하나다
4. **작업대에서 파일런이 제작되는가**
5. **보이는가** — 안 보이면 `research.md` 12장의 프리팹 참조 형태를 의심한다.
   `m_address`는 이제 자동 검사 대상이라 용의선상에서 내려갔다.
   **파일런이 2×2, 작업대가 4×2 타일로 보이는 것이 정상이다** — 아래 참조
6. **파일런이 꺼진 채로 설치되는가** (기획서 §5). 이때는 아무것도 보호하지 않아야 한다
7. **E로 켜지고 꺼지는가. 보석이 같이 빛나는가**
   ← 변형 매핑 확인 (`research.md` 13장의 미검증 추론). 안 바뀌면 대안이 적혀 있다.
   **실루엣은 절대 안 튀어야 한다** — 두 변형이 같은 텍스처를 쓰므로 튀면 다른 원인이다
7-1. **켤 때 짧은 빛과 소리, 끌 때 약한 역방향 연출이 나는가**
7-2. **기지에 들어설 때는 아무 소리도 안 나는가** ← "처음 반영" 가드 확인.
   나면 파일런이 스트리밍될 때마다 울리는 것이다
7-3. **이펙트가 범위 경계까지 퍼지지 않는가** (기획서 §7 — 퍼지면 렌즈가 필요 없어진다)
8. **범위가 맞는가** — 켠 뒤, 파일런 기준 10타일 안 상자는 안 부서지고 **밖 상자는 부서지는지**
9. **껐을 때 상자가 다시 부서지는가** ← **4단계의 핵심.** 안 되면 보호 해제가 안 도는 것
10. **원래 무적이던 게임 오브젝트는 여전히 안 부서지는가** ← 보호 해제의 안전장치 확인.
    코어·보스 구조물을 켰다 껐다 하며 때려본다
11. **껐다 켜면 다시 보호되는가**
12. **세이브/로드를 넘어 켜짐 상태가 유지되는가** (기획서 §5)
13. **켜진 파일런이 폭탄·곡괭이에 안 부서지고, 끄면 회수되는가** (기획서 §6)
14. **파일런 두 개를 겹쳐 놓고 하나만 끄면 보호가 유지되는가**
15. **나중에 놓은 파일런도 듣는가** — 상자를 먼저 놓고 그 옆에 파일런을 설치해서 켠다.
    `[NoBreakZone] active pylons` 로그가 뜨고 그 상자가 보호되면 재판정이 도는 것이다
16. 멀티플레이가 가능하면: **다른 플레이어 화면에서도 스프라이트가 바뀌는가**
17. 작업대에서 **렌즈가 제작되는가.** 인벤토리에서 **안 겹쳐지는가** (design.md §4)
18. **렌즈를 들면 켜진 파일런 주위에 닫힌 사각 윤곽 하나가 보이는가**
    ← 사다리 무늬·이중선이면 변 4개가 아니라 옛 타일 방식이 남은 것.
    **네 변이 갈라져 보이면** 평면 안 회전 각도가 틀린 것 (`PlaceEdge`의 오일러 각)
    ← 안 보이면 재질 문제를 제일 먼저 의심한다 (`research.md` 14장). 벽을 뚫고 보이는 것도 같은 원인
19. **내리면 사라지는가.** 인벤토리·지도를 열면 사라지는가
20. **꺼진 파일런은 경계선이 안 보이는가**
21. **경계선이 실제 보호 범위와 맞는가** — 선 바로 안쪽 상자는 안 부서지고 바깥은 부서지는지
22. 파일런이 여러 개 보일 때 **눈에 띄게 버벅이지 않는가** (이제 파일런당 4개)
22-1. **모서리에 틈이 없는가.** 선이 실제 경계와 맞는가 (선 바로 안쪽 상자는 안 부서지고 바깥은 부서지는지)
23. 마커가 **기지를 이상하게 만들지 않는가** (기획서 §7: 그러면 사용자가 모드를 지운다)
24. 작업대에서 **리모콘이 제작되는가**
25. **커서를 파일런에 올리고 우클릭하면 켜지고 꺼지는가**
    ← 안 되면 `SecondInteract_Pressed` 가정을 의심한다 (`research.md` 15장)
26. **E로 누른 것과 결과가 완전히 같은가** — 스프라이트·이펙트·보호 전부
27. **30타일 밖에서는 안 되는가.** 파일런이 아닌 것에 우클릭하면 아무 일도 안 나는가
28. **벽으로 둘러싼 파일런을 끌 수 있는가** ← 리모콘이 존재하는 이유 (design.md §4)
29. **2×1 작업대를 경계에 한 칸 걸쳐 놓으면 보호되지 않는가** (기획서 §6)
30. **완전히 안에 넣으면 보호되는가**
31. **파일런 둘에 나뉘어 걸친 물건은 보호되는가** ← 합집합 해석 확인
32. **파일런을 끄면 그 다중 타일 물건도 풀리는가** ← 거는 쪽/푸는 쪽이 어긋나지 않았는지
33. `Player.log`에 `no ObjectInfo for …` 경고가 뜨는가 ← 뜨면 그 오브젝트는 1×1로 취급된 것
34. **설정 파일이 생기고 네 항목이 다 보이는가** (`Player.log`의 `[NoBreakZone] config:` 줄)
35. **보호 범위를 11로 바꾸면 파일런을 껐다 켜지 않고도 좁아지는가**
36. **몹 피해 차단을 끄면** 몹이 상자를 부수고, **플레이어 곡괭이는 여전히 안 통하는가**
    ← 이번 단계에서 유일하게 추론에 기댄 부분
37. 범위 표시를 끄면 렌즈를 들어도 안 보이는가. 리모콘 사거리를 5로 줄이면 짧아지는가
38. **언어를 한국어로 바꿔도 아이템 이름이 (영어로라도) 뜨는가** ← 빈칸이면 구조가 틀린 것

유니티 Scriptable Data Editor로 우리 TextDataBlock을 열면 **슬롯마다 언어 이름이 보인다.**

### ⚠️ 스프라이트 결정 (a)의 근거가 틀렸다 — 32px 유지는 재확인됨 (2026-08-05)

**`spritePixelsToUnits`로는 월드 크기를 못 줄인다.** 32px 텍스처는 무슨 값을 넣든 **2×2 타일로
렌더된다** — `SpriteObject.PixelsPerUnit`이 코드에 박힌 `16f`이고, 월드 렌더 경로는 Sprite
서브에셋을 아예 거치지 않는다. 근거는 `research.md` 11장.

레퍼런스 실측으로도 확증됐다. `spritePixelsToUnits` 값은 **16이 146건, 100이 66건, 32는 0건**.
월드 텍스처는 16×16(1타일)·64×16(벨트 4타일)·48×48(포탈 3타일)로 전부 타일 배수이고,
배수가 아닌 것들은 전부 무기·방어구 **스프라이트시트**(`spriteMode: 2`)다.

*조치*는 그대로 둔다(32로 유지). 그 값이 실제로 먹는 곳은 인벤토리 아이콘이고 32px 텍스처에는
그게 맞는 값이다. 바뀐 것은 **기대치**뿐이다 — 파일런 2×2, 작업대 4×2로 보인다.

**사람이 32px 유지를 재확인했다 (2026-08-05).** 원래 논지 — "임시 스프라이트고 아트는 7단계
마감 항목이니 인게임에서 눈으로 본 뒤 고친다" — 가 그대로 유효하다. 체크포인트 1에서 **크기를
보고** 판단한다.

줄일 경우의 비용도 재봤다. 초안은 16px 그림의 2배 확대가 **아니다**(2×2 블록이 단색인 비율 73%).
색이 11개뿐이라 축소해도 형태는 읽히지만 무손실은 아니다.
줄이기로 하면 `genassets.py`의 `art`·`pixels_to_units` 두 줄이다.

확인된 것: **그레이스케일은 필수가 아니다.** 레퍼런스 모드는 컬러로 직접 그린다.
그레이스케일 + GradientMap은 스킨(색 교체)용 선택 기능이다.

### 파일런을 꺼내는 경로 (2026-08-05, 대상 벤치는 2026-08-06 교체)

콘솔 명령이 필요 없다. **작업대를 6단계에서 앞당겨 만들었다.**

```
자동화 테이블(바닐라)  ──레시피 주입──▶  Pylon Workbench  ──CraftingAuthoring──▶  파일런
```

레시피 주입이 없으면 이 모드는 인게임에서 **아예 도달할 수 없다.** 바닐라 작업대는 게임 것이라
우리가 고칠 수 없고, 베이킹을 가로채는 컨버터만이 거기에 레시피를 넣을 수 있다.
방법은 `research.md` 12장, **어느 벤치를 고를 수 있는지는 18장.**

앞당긴 범위는 **작업대 하나뿐**이다. 렌즈·리모콘은 6단계 그대로다.

### 4단계에서 한 것 (코드 완료·미검증)

**토글은 게임이 다 해준다.** `EntityMonoBehaviour.SetVariation(n)` 한 줄이 클라 예측·서버
반영·전원 전파를 처리하고, 세이브는 `ObjectDataCD`가 월드 세이브 대상이라 공짜다.
경로 전체는 `research.md` 13장.

| 한 것 | 어디 |
| --- | --- |
| E키 토글 | `Scripts/Graphics/NoBreakZonePylonGraphics.cs` — `Toggle()` |
| 다른 클라 화면 갱신 | 같은 파일 `ManagedLateUpdate()` — 게임이 안 해주는 유일한 부분 |
| `variationIsDynamic: 1` / 켜짐 스프라이트 | `genassets.py` 파일런 스펙 |
| 켜진 파일런만 수집 | `NoBreakZonePylonRegistrySystem.CollectPositions()` |
| 파일런 자체 무적 | 같은 파일 `ApplySelfProtection()` — 범위가 아니라 자기 변형에 연동 |
| **보호 해제** | `NoBreakZoneProtectionSystem.ReleaseUncovered()` |

마지막 줄이 3단계의 유일한 기능적 구멍이었다. 이제 파일런을 끄면 보호가 풀린다.
**`NoBreakZoneProtectedCD`가 붙은 것만 건드린다** — 원래부터 무적이던 게임 오브젝트는 그 태그를
받은 적이 없으므로 아무리 토글해도 안 부서진다. 2단계에 이 태그를 미리 만들어둔 이유가 이것이다.

### 5단계에서 한 것 (코드 완료·미검증)

| 한 것 | 어디 |
| --- | --- |
| 발광 = **같은 본체 텍스처 + `emissiveTexture`만 교체** | `genassets.py` 변형 스펙 |
| 발광 텍스처를 **초안 두 장의 차분에서 생성** | `genassets.py` `derive_emissive()` |
| 켜짐/꺼짐 이펙트·사운드 | `NoBreakZonePylonGraphics.PlayToggleFeedback()` |

기획서 §7의 "스프라이트는 한 종류만 만들고 발광 레이어를 켜고 끈다"를 구조적으로 만족한다 —
변형 0과 1이 **같은 텍스처 guid**를 가리키므로 실루엣이 어긋날 수가 없다. 초안 두 장은 알파가
완전히 같고 36픽셀(보석)만 달라서, 차분이 곧 발광부다.

`Textures/NoBreakZonePylonOn.png`는 지웠다. 4단계가 넣었던 "텍스처 두 장" 방식은 §7이 지정한
방식이 아니었다.

### 6단계에서 한 것 — 렌즈와 범위 표시 (코드 완료·미검증)

| 한 것 | 어디 |
| --- | --- |
| ~~경계 타일 계산~~ | 지웠다 — 아래 §9 항목 참조 |
| 렌즈 아이템 | `genassets.py` — **이 모드 첫 비설치물** |

고정 타일을 택했다("모니터가 큰 사람이 유리해지고, 멀티플레이에서는 플레이어마다 사거리가 달라진다").

### ⚠️ 범위 표시가 기획서 §9를 어기고 있었다 — 수정함 (2026-08-05)

§9가 숫자까지 대며 금지한 것을 그대로 만들었었다.

> **범위 표시를 타일마다 오브젝트를 생성해 구현하지 않는다.** 21×21이면 경계만 해도 80칸이다.

경계 타일마다 `GameObject`+`SpriteRenderer`를 하나씩 만들고 있었다. 파일런당 80개.
**플랜에 "파일런당 80칸"이라고 비용을 적어놓고도 이 문장과 대조하지 않았다** — `CoversRect` 때와
같은 실수다.

**변 4개로 바꿨다.** 보이는 것은 동일하다 — §9는 무엇을 그리냐가 아니라 어떻게 그리냐다.
선분 하나를 길이만큼 늘려 각 변을 만든다. 파일런당 80 → 4.

**덤으로 모양도 고쳐졌다.** 기존 마커는 속 빈 16×16 정사각형이라 경계 타일마다 깔리면 인접한
것끼리 변이 겹쳐 **사다리 무늬**가 됐다. 기획서 §7의 "아주 옅은 윤곽"이 아니었다.

`WriteBoundaryTiles`·`BoundaryTileCount`은 호출자가 사라져 **테스트와 함께 지웠다.**
안 불리는 테스트된 코드를 남기는 게 `CoversRect` 사고의 원인이었다.

### 범위 표시 방식 결정 (2026-08-05)

**경계선 전체**로 정했다 (사용자 판단). 기획서 §7 대안 조항이 "모서리 표식이나 아주 옅은 윤곽"을
제시했지만, 모서리만 두면 20타일 떨어진 점 사이를 눈으로 이어야 해서 경계 근처 판단이 어렵다.

마커는 **생성기가 그린다.** 색·두께·알파가 `genassets.py` 상수라 인게임에서 보고 바꾸기 쉽다.
기획서 §7이 "표시 때문에 기지가 이상해 보이면 그 자리에서 모드를 지운다"고 경고한 항목이므로
**옅게 유지하는 것이 기준**이다.

### 범위 표시는 5단계가 아니라 6단계다 (2026-08-05, 정정)

이전 문서들이 "범위 표시는 기획서 §7 전제가 틀렸으니 5단계 착수 전 승인 필요"라고 달아뒀는데,
§7 원문을 다시 읽으면 **파일런 쪽에는 범위 표시가 아예 없다.**

> 커서를 올려도, 파일런을 손에 들어도, **파일런을 켜고 꺼도** 범위는 보이지 않는다. 오직 렌즈뿐이다.

렌즈를 손에 든 동안에만 표시한다. 그러니 **렌즈와 함께 6단계에서 만든다.**

다만 문제 자체는 그대로 남아 있다 — **재사용할 바닐라 범위 표시가 게임에 없다.** 기획서 §7은
"게임에 이미 있는 방식을 따른다(아이템 수집기 등)"고 하는데 그런 컴포넌트를 못 찾았고,
레퍼런스 모드도 `SpriteRenderer`를 직접 풀링한다(`research.md` 10장).
**렌즈 착수 전에 §7의 대안 조항("바닥 텍스처를 덮지 않는 쪽 우선")으로 갈지 승인받는다.**

### 저장소 구조

단일 모드로 확정하고 커뮤니티 표준 레이아웃에 맞췄다. 근거와 레퍼런스는 `workflow.md` 11장.
`.cs`는 전부 `Scripts/` 아래이고, 그 안이 다시 `Logic/`·`Components/`·`Systems/`로 나뉜다.
3단계에서 `Prefabs/`·`Textures/`·`Data/SpriteAsset/`·`Data/TextDataBlock/Items/`가 붙었고
`SpriteAssetManifest.asset`은 레퍼런스 모드와 같이 모드 루트에 둔다.
문서·게임데이터·테스트·`preflight.py`·`genassets.py`는 `Editor/` 아래라 번들에 안 실린다.

**`Prefabs/`·`Textures/`·`Data/`의 에셋은 손으로 고치지 않는다.** `genassets.py`가 소유하고
매번 덮어쓴다. 바꾸려면 스펙을 고치고 재실행한다. (폴더 `.meta`만은 예외 — 한 번 만들고 다시
안 건드린다. guid가 바뀌면 그 아래 참조가 전부 끊긴다)

### 윈도우에서 처리해야 할 것 — ModBuilderSettings 추적 (미완)

**빌드 설정 에셋이 저장소 밖에 있어 버전 관리가 안 된다.** 모드 이름·의존성·`modPath`·
Linux 빌드 여부가 전부 윈도우 머신에만 있고, 그 머신이 사라지면 복원할 근거가 없다.

근거: `Data/NoBreakZone.asset`에는 `metadata`·`modPath` 필드가 없다(= 런타임 데이터 에셋이지
빌드 설정이 아니다). `CliBuild.cs`는 `Assets/NoBreakZone.asset`을 로드하고 빌드는 성공하므로,
그 파일은 저장소 밖 `Assets/` 바로 아래에 존재한다. 레퍼런스 모드는 4/4 모두 이 파일을
모드 폴더 안에 두어 추적한다.

윈도우에서 할 일:

1. 유니티 프로젝트 창에서 `Assets/NoBreakZone.asset`을 `Assets/NoBreakZone/` 안으로 드래그
   (`.meta`는 유니티가 같이 옮긴다)
2. 그 에셋의 `modPath`가 `Assets/NoBreakZone` 그대로인지 인스펙터에서 확인
3. `Editor/CliBuild.cs`의 `ModSettingsAssetPath` 상수를
   `"Assets/NoBreakZone/NoBreakZone.asset"` 으로 수정
4. `Editor/build.ps1` 실행해 종료 코드 0 확인 → 커밋
