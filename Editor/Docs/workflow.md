# No Break Area — 워크스페이스 정의서

작업 방식 정의 · v0.2

---

## 0. 이 문서에 대하여

**기획서가 "무엇을 만드는가"라면, 이 문서는 "어떻게 일하는가"이다.**

세션을 새로 시작할 때 이 문서와 기획서를 먼저 읽는다. 그것만으로 지금 어디까지 왔고 무엇을 해야 하는지 파악할 수 있어야 한다.

이 문서에는 아직 채워지지 않은 부분이 있다. SDK의 빌드 방식이나 배포 절차처럼 **직접 확인해야 알 수 있는 것들**이다. 해당 절에는 `확인 필요`로 표시해두었고, 조사가 끝나면 그 자리를 채운다.

---

## 1. 역할 분담

| 하는 일 | 주체 |
| --- | --- |
| 게임 코드 디컴파일·조사 | AI |
| 코드 작성·수정 | AI |
| 빌드 | AI |
| 로그 읽기·원인 분석 | AI |
| 커밋 / PR / 릴리즈 | AI |
| 문서 갱신 | AI |
| **게임 실행·플레이 테스트** | **사람** |
| **화면을 눈으로 확인하는 판단** | **사람** |
| **유니티 에디터 GUI 조작** | **사람** |
| **최종 스프라이트 제작** | **사람** |
| **계정·약관 동의** | **사람** |
| **배포(deploy) 실행** | **사람** |
| **설계와 밸런스 결정** | **사람** |

AI가 못 하는 일은 대부분 **"실제로 게임을 해보는 것"**에 몰려 있다. 그래서 모든 작업은 결국 사람의 확인을 거쳐야 끝난다.

## 2. 작업 사이클

```
대화 → 플랜 → 승인 → 작업 → 빌드 → 사람이 검증 → 커밋 → PR → 머지
```

### 대화 단계

**이 단계에서는 파일을 수정하지 않는다.** 읽기, 조사, 질문, 제안만 한다.

무엇을 만들지 합의하는 자리다. 합의가 끝나기 전에 코드를 건드리면 대화가 검토가 아니라 사후 확인이 된다.

조사를 위한 읽기와 디컴파일은 이 단계에서 해도 된다. 오히려 권장한다. 정확한 정보를 바탕으로 대화해야 하기 때문이다.

### 플랜 단계

**건너뛸 수 없다.** 사람이 "바로 해"라고 명시적으로 말하지 않는 한, 크기와 무관하게 모든 작업은 플랜과 승인을 거친다. 질문에 답을 받은 것은 승인이 아니다. 승인은 플랜 승인뿐이다.

플랜에는 아래가 반드시 들어간다.

- 무엇을 바꾸는가 (한 문장)
- 건드릴 파일 목록
- 새로 만들 파일 목록
- **사람이 게임에서 무엇을 확인해야 하는가**
- 예상되는 위험이나 불확실한 부분
- 기획서의 어느 항목에 해당하는가

마지막 항목이 중요하다. 기획서에 없는 작업이면 그 사실을 먼저 밝히고 승인을 받는다.

### 작업 단계

승인된 플랜의 범위만 작업한다. 진행 중 플랜을 벗어날 필요가 생기면 **멈추고 알린다.** 임의로 범위를 넓히지 않는다.

### 검증 단계

빌드까지 마친 뒤, 사람에게 **무엇을 어떻게 확인하면 되는지** 구체적으로 알린다.

> 예: "빌드했습니다. 기지에 상자를 놓고 폭탄을 터뜨려 보세요. 상자가 살아남고, 근처 광석 덩어리는 정상적으로 부서져야 합니다."

## 3. 완료의 정의

**코드 완료와 검증 완료를 구분한다.**

| 상태 | 의미 |
| --- | --- |
| 코드 완료 | 작성과 빌드가 끝남. 아직 아무것도 확인되지 않음 |
| 검증 완료 | 사람이 게임에서 의도대로 동작함을 확인함 |

**커밋과 PR은 검증 완료 후에 한다.** 코드가 완성됐다는 이유만으로 "완료했습니다"라고 보고하지 않는다.

## 4. 개발 루프

**확정됨** (2026-07-27 첫 빌드 성공). 근거는 `research.md` 2·6장.

```
코드 수정 → 유니티 에디터 닫기 → Editor/build.ps1 → 게임 Mods 폴더 갱신
         → 사람이 게임 실행/재로드 → 확인 → Player.log 확인
```

| 항목 | 값 |
| --- | --- |
| 빌드 명령 | `powershell -File Editor/build.ps1` (**윈도우 전용**) |
| 종료 코드 | `0` 성공 / `1` 실패 / `2` 에디터가 열려 있음 |
| 산출 경로 | `…\Core Keeper\CoreKeeper_Data\StreamingAssets\Mods\NoBreakZone\` |
| 로그 | `%LOCALAPPDATA%Low\Pugstorm\Core Keeper\Player.log` |

빌드는 유니티 프로젝트가 있는 **윈도우 머신에서만** 된다. 맥 체크아웃은 문서·계획·코드 편집용 미러다.
절차 상세는 `.claude/skills/build/SKILL.md`.

남은 미확인: 게임을 재시작하지 않고 모드를 다시 불러올 수 있는지 (`research.md` 7장).

### 목표: 유니티 에디터는 설치만 하고 열지 않는다

작업자는 유니티 경험이 없다. 그리고 이 프로젝트에서 사람이 해야 하는 일은 **게임을 실행해 확인하는 것**에 집중되어야 한다.

따라서 아래는 가능한 한 코드와 명령으로 처리한다.

- 빌드 — 유니티 배치 모드 커맨드라인
- 스프라이트 임포트 설정 — `.meta` 파일을 직접 작성
- 프리팹 생성과 컴포넌트 부착 — 에디터 스크립트로 프로그래밍적으로 처리
- 모드 폴더 배치, 로그 확인, 에셋 추출 — 스크립트

**사람이 제공하는 것은 PNG 파일까지다.** 그것을 프로젝트에 넣고 설정하고 오브젝트에 연결하는 것은 AI가 한다.

자동화가 불가능한 지점을 발견하면 우회하려 애쓰기 전에 **먼저 알린다.** 에디터를 여는 것이 정답일 수도 있다.

### 왜 중요한가

**이 루프의 속도가 프로젝트 전체 속도를 정한다.** 한 번 도는 데 2분이 걸리면 하루에 수십 번 반복하는 작업이 몇 시간이 된다.

자동화할 수 있는 부분은 스크립트로 묶는다. 목표는 **사람이 게임만 켜면 되는 상태**다.

## 5. 깃허브 운영

1인 프로젝트이므로 가볍게 간다.

### 브랜치

- `main` — 항상 동작하는 상태를 유지
- `feat/이름` — 기능 작업
- `fix/이름` — 버그 수정
- `chore/이름` — 문서, 설정, 정리

develop 브랜치는 두지 않는다. 혼자서는 과하다.

### 커밋

작업 중에는 자주 해도 된다. 메시지는 **무엇을 왜 했는지**가 드러나게 쓴다.

```
feat: 파일런 범위 안 설치물 피해 차단
fix: 파일런 제거 후 보호가 유지되던 문제
chore: 기획서 v1.3 반영
docs: 조사 결과 기록 - 피해 시스템 경로
```

### PR

**혼자여도 PR을 만든다.** 리뷰 때문이 아니라 변경 내역이 한 덩어리로 묶여 기록되기 때문이다. 나중에 "이 기능을 언제 왜 넣었는지" 추적할 수 있고, 문제가 생기면 통째로 되돌리기 쉽다.

PR 본문에는 무엇을 바꿨는지, **사람이 게임에서 무엇을 확인했는지**를 적는다.

### 릴리즈

깃허브 릴리즈는 **기록**이다. 자주 찍어도 된다. 잘못 찍으면 지우고 다시 하면 된다.

버전은 `0.1.0` 형태로 시작한다. 검증된 기능이 늘어나면 마이너를 올리고, 사용자에게 배포할 만한 상태가 되면 `1.0.0`으로 간다.

## 6. release와 deploy는 다르다

| | release | deploy |
| --- | --- | --- |
| 하는 일 | 태그 + 깃허브 릴리즈 + 노트 | mod.io / 스팀 창작마당 업로드 |
| 대상 | 기록 | 실제 사용자 |
| 되돌리기 | 가능 | 사실상 불가능 |
| 실행 | AI | **사람** |

**둘을 한 명령에 묶지 않는다.** "릴리즈 해줘"가 배포까지 실행되면 사고가 된다.

deploy에서 AI가 하는 일은 **준비까지**다. 빌드 산출물을 만들고, 점검 목록을 확인하고, 업로드할 파일과 설명문을 정리한 뒤 **멈추고 알린다.** 실제 업로드는 사람이 한다.

deploy는 **release가 선행된 커밋에 대해서만** 진행한다. 어떤 코드가 배포됐는지 항상 추적 가능해야 한다.

### 배포 절차

`확인 필요` — mod.io와 스팀 창작마당 업로드 방식을 확인한 뒤 채운다.

- SDK에 내장된 창작마당 업로드 기능의 사용법
- mod.io 업로드 절차
- 필요한 메타데이터 (태그, 설명, 썸네일, 의존성)
- 버전 갱신 시 주의사항

## 7. 기록 규칙

세션이 바뀌면 맥락이 사라진다. **기록이 없으면 같은 조사를 반복한다.**

모든 문서는 `Editor/Docs/` 아래에 있다. `Editor/` 하위라 빌드된 모드 번들에는 포함되지 않는다.
**파일명은 ASCII, 본문은 한글**이다 — 맥/윈도우를 오가도 경로가 깨지지 않게 하기 위해서다.

| 파일 | 내용 |
| --- | --- |
| `Editor/Docs/design.md` | 기획서. 무엇을 만드는가 |
| `Editor/Docs/workflow.md` | 이 문서. 어떻게 일하는가 |
| `Editor/Docs/status.md` | 지금 몇 단계인지, 다음에 할 일 |
| `Editor/Docs/research.md` | 게임 코드에서 알아낸 것 |
| `Editor/Docs/failures.md` | 시도했으나 안 된 것과 그 이유 (필요해지면 만든다) |
| `Editor/GameData/` | DB 덤프로 뽑은 정적 참조 (`object_flags.csv`) |
| `Editor/Docs/art/` | 스프라이트 초안과 생성 스크립트 |

갱신은 `/log` 스킬로 한다 (`.claude/skills/log/`).

### status.md

**가장 자주 갱신한다.** 작업이 끝날 때마다 반영한다. 세션을 새로 시작한 사람이 이 파일만 봐도 이어갈 수 있어야 한다.

### research.md

디컴파일이나 실험으로 알아낸 사실을 남긴다. 클래스 이름, 컴포넌트 구조, 동작 방식 등. **기획서의 `확인 필요` 항목이 해결되면 여기에 근거를 남기고 `design.md`를 갱신한다.**

### failures.md

**성공보다 중요하다.** "이 방법을 써봤는데 이래서 안 됐다"를 남기지 않으면 같은 시도를 반복한다. 이 프로젝트는 미확인 항목이 많아 특히 그렇다.

## 8. 멈추고 물어봐야 할 때

아래 상황에서는 **작업을 멈추고 사람에게 확인**한다.

- 기획서에 없는 기능을 추가해야 할 것 같을 때
- 기획서의 결정을 바꿔야 할 근거를 발견했을 때
- 승인된 플랜의 범위를 벗어나야 할 때
- 오브젝트 ID를 바꿔야 할 상황이 생겼을 때
- 세이브 데이터 구조에 영향을 주는 변경이 필요할 때
- 조사 결과가 기획서의 전제와 다를 때
- 성능에 눈에 띄는 영향이 있을 것 같을 때

**특히 마지막 세 가지는 조용히 넘어가면 나중에 훨씬 비싸진다.**

## 9. 금지 사항

- **승인된 플랜 없이 파일을 수정하지 않는다.** 명시적 지시("바로 해")가 있을 때만 예외다
- **오브젝트 ID를 변경하지 않는다.** 세이브에 기록되므로 변경하면 기존 세이브가 손상된다
- 사람의 검증 없이 완료로 처리하지 않는다
- 대화 단계에서 파일을 수정하지 않는다
- deploy를 실행하지 않는다
- 기획서의 결정을 임의로 바꾸지 않는다. 근거가 있으면 제안하고 승인을 받는다
- 결정 기록이 달린 항목을 "더 나은 방법"이라며 되돌리지 않는다. 이미 검토하고 뺀 것들이다

## 10. 스킬

반복되는 절차는 스킬로 정의해 매번 같은 방식으로 처리한다. **이 프로젝트 고유의 절차만** 만든다.

| 스킬 | 상태 | 하는 일 |
| --- | --- | --- |
| `.claude/skills/build` | 있음 | 빌드 절차. 윈도우 전용이라는 사실과 종료 코드 해석 포함 |
| `.claude/skills/log` | 있음 | `status.md` / `research.md` / `failures.md` 갱신 |
| deploy-prep | 없음 | 배포 절차(6장)가 확인되면 만든다 |

commit · pr · release는 **만들지 않는다.** 전역 gstack 스킬(`/ship`, `/review`)과 중복이다.
다만 이 프로젝트의 추가 제약(검증 완료 전 커밋 금지, 영문 subject)은 `CLAUDE.md`에 적혀 있고 그쪽이 우선한다.

## 11. 폴더 구조

**확정됨.** 저장소 루트가 곧 유니티의 `Assets/NoBreakZone/`, 즉 **모드 번들 경로(modPath)**다.
이게 구조를 규정하는 유일한 제약이다.

레이아웃은 커뮤니티 표준을 따른다. 공개된 SDK 단일 모드 저장소
(moorowl/CustomizableMapBackground, budak7273, limoka/SecureAttachment, germanoeich/Cornucopia)에서
공통으로 나타나는 형태다.

```
no-break-zone/                  = Assets/NoBreakZone/ = modPath
├─ .claude/                     작업 하네스. 점으로 시작 → 유니티가 안 읽음
├─ .github/                     PR 템플릿
├─ CLAUDE.md · README.md · LICENSE.md   루트 문서는 여기까지. 짧게 유지
├─ NoBreakZone.asmdef
├─ Scripts/                      런타임 코드 (.cs는 전부 여기)
├─ Data/NoBreakZone.asset        런타임 모드 데이터
└─ Editor/                       ← 번들 제외 구역
   ├─ CliBuild.cs · build.ps1    빌드 도구
   ├─ Docs/                      문서 + art/ (스프라이트 초안)
   └─ GameData/                  DB 덤프 참조
```

**아직 없지만 이름이 정해진 것** — 실제 파일이 생길 때 만든다. 빈 폴더를 미리 만들면
`.meta`만 남는 쓰레기가 된다.

| 경로 | 언제 | 용도 |
| --- | --- | --- |
| `NoBreakZone.asset` | 윈도우 작업 시 | **ModBuilderSettings**(빌드 설정). 지금 저장소 밖에 있어 추적이 안 된다 |
| `Scripts/Systems/` · `Scripts/Components/` | 3단계 | 파일이 늘면 나눈다 |
| `Textures/` | 3단계 | 스프라이트 PNG |
| `Prefabs/` | 3단계 | 커스텀 오브젝트 프리팹 |
| `Localization/Localization.csv` | 3단계 | SDK가 특별 취급하는 경로 |
| `NoBreakZone_modio.asset` | 7단계 | 배포 채널별 빌드 설정 |

**핵심 규칙 세 개:**

1. **modPath 아래의 거의 모든 자산이 번들에 실린다.** `ModBuilder`는 `.cs`·`.dll`·`Conf/`·
   `Localization/`·`Editor/`·`CodeGen/`을 **제외한 전부**를 AssetBundle로 쓸어담는다
   (`research.md` 6장). → **배포 대상이 아닌 것은 `Editor/` 아래에 둔다.**
2. **모든 자산에 `.meta`가 붙는다.** 이름을 바꾸거나 옮길 때는 `.meta`도 **같이** 옮긴다.
   안 그러면 유니티가 GUID를 새로 발급해 참조가 끊긴다. 새 폴더를 만들면 폴더 `.meta`도 만든다.
3. **점(`.`)으로 시작하는 폴더는 유니티가 자산으로 읽지 않는다.** `.claude/`·`.github/`가
   modPath 안에 있어도 번들과 무관하고 `.meta`도 필요 없다.
