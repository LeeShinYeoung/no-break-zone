# No Break Zone

Core Keeper 모드 기획서 · v1.3

---

## 1. 한 줄 정의

기지에 설치해두면 주변 일정 범위 안의 설치물이 **피해로 파괴되지 않게** 만들어주는 장치.

## 2. 왜 만드는가

강력한 폭발 무기를 실수로 기지 안에서 사용하면 상자, 작업대, 바닥이 한 번에 날아간다. 되돌릴 방법이 없고 상자 안 내용물까지 잃는다.

기존 모드 중에는 이 문제를 정면으로 해결하는 것이 없다. 가장 근접한 SecureAttachment는 로봇 팔·드릴 같은 일부 기계만 대상으로 하고, 1.0 이전 BepInEx 시절 모드라 현재 버전에서 동작하지 않을 가능성이 높다.

## 3. 설계 원칙

이 모드가 지켜야 할 네 가지. 기능을 추가할지 말지 고민될 때 여기로 돌아온다.

**1. 켜져 있으면 아무도 손댈 수 없다.**
보호는 예외를 두지 않는다. 사고든 의도된 철거든 똑같이 막는다. 기지를 수정하고 싶으면 파일런을 끄러 가는 것이 정상적인 절차다.

규칙이 하나뿐이라 사용자가 외울 예외가 없고, "이건 되는데 저건 왜 안 되지"가 발생하지 않는다. 무엇보다 게임 내부에서 채굴 피해와 전투 피해가 구분되는지에 프로젝트가 걸리지 않는다.

**2. 상태가 눈에 보여야 한다.**
"켜놓은 줄 알았는데 꺼져 있었다"가 이 모드의 최악의 실패다. 켜짐/꺼짐과 보호 범위는 화면에서 즉시 확인 가능해야 한다.

**3. 있는지 없는지 모르게 돌아가야 한다.**
보호 기능 때문에 프레임이 떨어지면 사용자는 모드를 지운다. 기지가 커지고 자동화 설비가 늘어나도, 멀티플레이 인원이 많아져도 체감 차이가 없어야 한다. 성능은 나중에 손볼 항목이 아니라 처음부터 지켜야 할 제약이다.

**4. 되돌릴 수 있어야 한다.**
보호가 강력한 만큼, 무언가 잘못됐을 때 빠져나올 수단이 게임 안에 있어야 한다. 현재는 리모콘이 그 역할을 한다.

## 4. 구성 요소

이 모드는 네 가지 물건을 추가한다.

| 구분      | 표시 이름 (EN)  | 표시 이름 (KO) | 오브젝트 ID             | 스택     |
| --------- | --------------- | -------------- | ----------------------- | -------- |
| 보호 장치 | No Break Pylon  | 파일런         | `NoBreakZone.Pylon`     | 가능     |
| 범위 확인 | Pylon Lens      | 파일런 렌즈    | `NoBreakZone.Lens`      | **불가** |
| 원격 조작 | Pylon Remote    | 파일런 리모콘  | `NoBreakZone.Remote`    | **불가** |
| 제작      | Pylon Workbench | 파일런 작업대  | `NoBreakZone.Workbench` | 가능     |

**ID는 한 번 정하면 바꾸지 않는다.** 오브젝트 ID는 세이브에 기록되므로, 나중에 변경하면 기존 세이브가 손상된 상태로 로드된다. 접두사 `NoBreakZone.`는 다른 모드와의 충돌을 막기 위한 것이다.

**렌즈와 리모콘은 스택되지 않는다.** 여러 개를 가질 이유가 없는 물건이고, 겹쳐지면 인벤토리에서 개수만 헷갈린다.

**표시 이름에는 모드 이름을 붙이지 않는다.** 게임 안에서는 어느 모드에서 왔는지보다 그 물건이 무엇인지가 중요하다. 렌즈·리모콘·작업대에 `Pylon`을 붙인 것은 모드 표시가 아니라, 셋 다 파일런에 딸린 물건이기 때문이다.

### 진행도와 재료

**잊혀진 유적(Forgotten Ruins) 도달이 실질적인 관문이다.**

고대 보석과 기계부품은 유적의 도시 구역이 최상급 산지로, 케이블링 계열 적과 부술 수 있는 고대 오브젝트에서 나온다. 코어를 활성화한 뒤에는 망토 상인에게 고대 동전 55개로 구매할 수도 있다.

주석 단계에 두는 안도 검토했으나, 고대 유물 같은 장치라는 성격에 재료가 맞고 유적에 도달할 무렵이면 지킬 만한 기지가 갖춰져 있다는 점에서 이쪽을 택했다.

기본 금속을 주석이 아니라 **철**로 잡은 이유도 같다. 실제로 제작을 막는 것은 고대 보석과 기계부품이므로, 주석을 쓰면 재료 등급과 제작 시점이 어긋난다. 철광석은 유적에서도 나오므로 자연스럽게 맞물린다.

작업대를 어디서 만들지도 원래 같은 이유로 철 계열에 두려 했다. 낮은 작업대에 넣으면 레시피는 보이는데 재료가 없어 못 만드는 상태가 오래 이어지기 때문이다. **이 결정은 뒤집혔다** — 철 작업대에는 물리적으로 자리가 없었다. 아래 작업대 항목의 결정 기록을 본다.

고대 보석은 파일런에 집중시키고 나머지는 싸게 둔다. 파일런 개수에 제한이 없으므로 여러 개를 놓게 되는데, 보석이 많이 들면 부담이 커진다. 개당 1~2개를 넘기지 않는다.

수량은 실제 플레이 후 조정한다.

### 표기 언어

코어 키퍼는 13개 언어를 지원한다. 영어, 간체 중국어, 번체 중국어, 태국어, 스페인어, 독일어, 일본어, 한국어, 프랑스어, 이탈리아어, 브라질 포르투갈어, 러시아어, 우크라이나어.

1차 배포는 **영어와 한국어**만 한다. 번역할 문자열은 아이템 이름과 설명문, 설정 항목 정도로 적지만, 기계 번역으로 13개를 채우면 어색한 문장이 그대로 나간다.

다만 **구조는 처음부터 13개 언어를 받을 수 있게 만든다.** 배포 후 사용자가 번역을 보내오면 파일만 추가해서 반영할 수 있어야 한다.

### 파일런 (No Break Pylon)

기능의 본체. 외형은 오벨리스크 형태 — 세로로 긴 돌기둥에 발광 부위가 박힌 모습.

| 항목      | 내용                                      |
| --------- | ----------------------------------------- |
| 분류      | 설치물 / 기계                             |
| 차지 공간 | 1×1 타일                                  |
| 제작처    | 작업대                                    |
| 제작 재료 | 철 + 고대 보석 1~2 + 기계부품             |
| 회수      | 비활성 상태에서 일반 설치물처럼 회수 가능 |

> 주변의 물건을 보호한다. 켜져 있는 동안에는 어떤 충격도 그 안의 것들을 부수지 못한다.
> 범위를 확인하려면 렌즈가 필요하다.

### 렌즈 (Pylon Lens)

손에 들고 있는 동안 **화면 안의 모든 파일런 범위를 동시에 보여주는** 도구.

| 항목      | 내용                                    |
| --------- | --------------------------------------- |
| 분류      | 도구 (손에 드는 물건, 착용 장비가 아님) |
| 제작처    | 작업대                                  |
| 제작 재료 | 철 + 고대 보석 1                        |
| 소모      | 없음. 내구도도 두지 않는다              |

착용이 아니라 손에 드는 방식으로 정한 이유는 두 가지다. 장신구 칸을 잡아먹지 않고, "손에 든 물건이 범위를 보여준다"는 규칙으로 파일런과 동작이 통일되기 때문이다.

> 파일런의 파편을 깎아 만든 렌즈. 들여다보면 보호의 경계가 드러난다.

### 리모콘 (Pylon Remote)

**멀리서 파일런을 켜고 끄는** 도구. 파일런 앞에서 E를 누르는 것을 원거리에서 할 수 있게 해줄 뿐, 그 이상은 하지 않는다.

| 항목      | 내용                                              |
| --------- | ------------------------------------------------- |
| 분류      | 도구 (손에 드는 물건)                             |
| 제작처    | 작업대                                            |
| 제작 재료 | 철 + 기계부품                                     |
| 조작      | 커서를 파일런에 올리고 **우클릭**                 |
| 효과      | 그 파일런 하나를 켜거나 끈다 (E를 누른 것과 동일) |
| 사거리    | 플레이어 기준 30타일 반경 (설정 가능)             |
| 벽·시야   | 무시한다. 막혀 있어도 통한다                      |
| 소모      | 없음                                              |

**E의 원거리판일 뿐이다**
리모콘은 새로운 기능을 만들지 않는다. 파일런 앞에서 E를 누르는 것과 결과가 완전히 같고, 거리만 다르다. 대상이 파일런 하나뿐이므로 "여러 파일런을 한꺼번에" 같은 확장은 하지 않는다.

**우클릭에 배치한 이유**
코어 키퍼는 마우스 배치가 일반적인 게임과 반대다. 게임플레이 중 기본 바인딩은 **공격이 좌클릭, 사용(Use)이 우클릭**이다. 아이템을 쓰는 입력은 우클릭이므로 리모콘의 동작도 여기에 온다.

**사거리를 화면이 아니라 고정 타일로 정의한 이유**
"화면 안"을 문자 그대로 구현하면 해상도와 줌 배율에 따라 사거리가 달라진다. 모니터가 큰 사람이 유리해지고, 멀티플레이에서는 플레이어마다 사거리가 달라진다. 고정 반경으로 두고 설명에는 "대략 화면 범위"로 안내한다.

**피드백은 리모콘 자체가 준다**
사용하면 리모콘의 화면이 짧게 깜빡이고 효과음이 난다. 벽에 갇힌 파일런은 파일런 쪽 이펙트가 잘 보이지 않으므로, 작동 여부를 손에 든 물건이 알려줘야 한다.

> **리모콘이 필요한 이유 (결정 기록)**
>
> 파일런을 켠 뒤 그 주위를 자기가 놓은 벽으로 둘러싸면 게임이 막힌다. 그 벽도 보호 대상이라 캘 수 없고, 파일런에도 손이 닿지 않는다.
>
> 리모콘은 이 상황을 게임 안에서 푼다. 덤으로 파일런까지 걸어가지 않아도 되는 편의가 생긴다.
>
> 다만 그 이상으로 키우지 않는다. "사거리 안 모든 파일런 일괄 조작" 같은 확장은 검토했다가 뺐다. 리모콘의 존재 이유는 손이 닿지 않는 파일런을 조작하는 것 하나뿐이고, 기능이 늘어나면 상태가 뒤섞이는 문제와 실수로 전체 보호를 꺼버리는 위험이 따라온다.

렌즈와 리모콘은 역할이 나뉜다. **렌즈는 보고, 리모콘은 조작한다.**

### 작업대 (Pylon Workbench)

보호 관련 물건을 만드는 전용 작업대.

| 항목           | 내용                                              |
| -------------- | ------------------------------------------------- |
| 분류           | 설치물 / 작업대                                   |
| 차지 공간      | 1×1 타일                                          |
| 제작처         | **자동화 테이블 (Automation Table)**              |
| 제작 재료      | 철 + 나무 + 기계부품 1                            |
| 제작 가능 품목 | 파일런, 렌즈, 리모콘                              |

> **전용 작업대로 바꾼 이유 (결정 기록)**
>
> 처음에는 기존 작업대에 레시피만 추가할 계획이었다. 전용 작업대는 스프라이트와 UI 부담이 두 배로 늘기 때문이다.
>
> 바꾼 이유는 **확장성**이다. 앞으로 보호 관련 물건이 늘어났을 때 여러 작업대에 흩어져 있으면 사용자가 찾기 어렵고, 이 모드가 무엇을 제공하는지 한눈에 들어오지 않는다. 전용 작업대는 앞으로 추가될 것들의 집이 된다.

> **제작처를 철 작업대에서 자동화 테이블로 옮긴 이유 (결정 기록, 2026-08-06)**
>
> **철 작업대에는 자리가 없다.** 제작 UI는 창 3개 × 6칸이라 벤치당 18개가 상한인데, 철 작업대는 자기 레시피로 정확히 18개를 채운다. 구리·주석·전자 작업대도 전부 18이라, 18은 게임이 벤치를 채우는 기준값이다. 공식 모딩 문서도 반대편에서 같은 말을 한다 — *"each workbench can have AT MOST 18 slots. You cannot exceed this value."*
>
> 게다가 철 작업대는 기본·구리·주석 작업대를 **흡수한다.** 흡수된 벤치는 레시피 목록을 구역으로 쪼개고 UI는 한 번에 한 구역만 그린다(제작창 옆 ▲▼ 화살표가 그 구역을 넘긴다). 그래서 버퍼가 18 × 4 = 72이고, 끝에 붙인 우리 레시피는 어느 구역에도 안 들어가 **영영 그려지지 않는다.** 자리가 남아 있었더라도 화살표가 있는 한 붙이는 방식은 성립하지 않았다.
>
> **자동화 테이블은 18칸 중 6개만 쓰고 아무것도 흡수하지 않는다.** 목록 전체가 그려지므로 붙이기만 하면 된다. ConveyorTunnelMod가 같은 벤치에 같은 컨버터 형태로 붙이고, DummyMod도 여기에 넣는다 — 둘 다 배포된 채 동작한다. 파일런이 기계 장치이고 기계부품을 재료로 쓰니 주제도 맞는다.
>
> **감수하는 것**: 자동화 테이블은 주석 단계에서 만들 수 있으므로, 유적에 도달하기 전까지 재료가 없는 회색 레시피가 보인다. 위에서 피하려 했던 상황이 그대로 생긴다. 철 단계에서 자리가 남는 곳은 보석 세공대(6/18)와 열쇠 주조대(7/18)뿐인데, 둘 다 보호 장치를 찾을 이유가 없는 벤치라 **발견 가능성이 더 나빠진다**고 판단했다.
>
> **재료는 바꾸지 않는다.** 실질적 관문은 고대 보석과 기계부품이라는 위 논지가 그대로 유효하다. 제작처가 앞당겨져도 재료가 관문을 유지한다.
>
> 벤치별 실측값과 UI 구조는 `research.md` 18장.

> **차지 공간을 2×1에서 1×1로 줄인 이유 (결정 기록, 2026-08-06)**
>
> **인게임에서 처음 놓아보고 결정했다.** 사용자 판단이다.
>
> 원래 2×1로 정한 근거는 "작업대는 큰 물건"이라는 인상이었지 측정이 아니었다. 실제로 놓아보니
> 두 가지가 겹쳐 있었다 — 발자국이 두 칸인 것과, **스프라이트가 발자국보다 두 배 크게
> 그려지던 것**(아래 스프라이트 규격 항목). 후자는 버그였고, 고치고 나서도 **좁은 기지에서
> 두 칸을 먹는 작업대는 손해**라는 판단이 남았다.
>
> 게임 자신도 작업대를 1×1로 만든다. SDK 예제 작업대가 `prefabTileSize 1×1`에 16×18 아트다.
>
> **여파**: `Prefabs/NoBreakZoneWorkbench.prefab`의 `prefabTileSize`만 바뀐다. 오브젝트 ID는
> 그대로라 세이브는 안 깨진다. 다만 이미 설치된 개체는 회수했다 다시 놓는 편이 깔끔하다.
> §6의 "모든 타일이 범위 안에 들어와야 보호된다"는 규칙은 그대로다 — 1×1이면 자동으로 만족되고,
> 다중 타일 판정 코드는 파일런 여러 개에 걸친 다른 설치물을 위해 계속 필요하다.

## 5. 활성화 방식

- 파일런에 다가가 **상호작용 키(E)를 누르면 켜지고, 다시 누르면 꺼진다.**
- 클릭은 쓰지 않는다. 좌클릭은 공격, 우클릭은 아이템 사용에 이미 배정되어 있어 파일런을 때리거나 들고 있던 물건을 쓰게 된다. E는 상자를 열고 작업대를 여는 것과 같은 "오브젝트 상호작용" 키이므로 파일런에도 이쪽이 맞다.
- 멀리서 조작하려면 **리모콘**을 쓴다. 동작은 E와 완전히 같다.
- **전기는 필요 없다.** 발전기도 전선도 연결하지 않는다.
- 상태는 **세이브/로드를 넘어 유지된다.**
- 새로 설치했을 때의 초기 상태는 **꺼짐**.
- 상태를 확인할 수 없는 문제가 생기면 **켜짐으로 간주**한다. (꺼진 채 부활하는 것보다 안전)

## 6. 보호 규칙

이 모드의 핵심. 아래 표가 곧 사양이다.

### 보호 범위

파일런을 중심으로 한 **정사각형 N×N 타일**. 원형이 아니다.

- N = 21 (파일런 기준 사방 10타일). 설정으로 변경 가능
- 판정은 가로/세로 거리 중 큰 값이 10 이하인가로 한다
- 파일런이 꺼져 있으면 범위는 존재하지 않는다

### 무엇을 막고 무엇을 통과시키는가

| 상황                                   | 결과                                     |
| -------------------------------------- | ---------------------------------------- |
| 플레이어의 폭발 무기가 상자에 닿음     | **막는다**                               |
| 플레이어의 일반 공격이 작업대에 빗맞음 | **막는다**                               |
| 몹이 설치물을 공격함                   | **막는다**                               |
| 보스 공격·환경 피해가 설치물에 닿음    | **막는다**                               |
| 플레이어가 곡괭이·망치로 설치물을 철거 | **막는다**                               |
| 플레이어가 설치물을 집어 올림          | **막는다**                               |
| 플레이어가 벽·바위·광석을 채굴         | **막는다**                               |
| **드릴이 광석 덩어리를 캐서 고갈시킴** | **통과시킨다**                           |
| **작물을 수확함**                      | **통과시킨다**                           |
| **폭발이 구역 안 맨땅을 파헤침**       | **막는다**                               |
| **호미로 구역 안에 새 밭을 갊**        | **막는다** (아래 결정 기록)              |
| **삽으로 구역 안 바닥재를 걷어냄**     | **통과시킨다** (아래 결정 기록)          |
| 새 물건을 설치                         | 통과시킨다                               |
| 플레이어 자신이 피해를 입음            | 통과시킨다 (플레이어는 보호 대상이 아님) |
| 몹이 피해를 입음                       | 통과시킨다                               |

규칙은 하나다. **켜져 있는 동안 범위 안의 설치물은 어떤 방법으로도 사라지지 않는다.**

가해자가 누구인지, 어떤 도구를 들었는지, 의도적인지 사고인지 따지지 않는다. 기지를 수정하려면 파일런을 끄면 된다.

설치는 막지 않는다. 파괴만 막는 것이므로 보호 중에도 새 물건을 놓는 것은 자유롭다.

#### 결정 기록 — 지면 편집 (2026-09-05)

**호미질도 같이 막는다.** 호미가 밭을 가는 것과 폭발이 지면을 파헤치는 것은 타일 버퍼에 **완전히
같은 항목**(`Add dugUpGround`)으로 도착하고, 그 항목에는 가해자가 안 적혀 있다. 데이터로 구분할
방법이 없으므로 둘 다 막는다. 위의 한 줄짜리 규칙과 같은 결이다 — **밭을 갈려면 파일런을 끈다.**
게임 자체도 같은 모양이다: 게임의 immunity zone 안에서는 호미와 삽이 스스로 물러난다.

**삽으로 바닥재를 걷어내는 것은 막지 못한다.** 막으려고 했고, 막으면 안 되는 이유를 찾았다.
`PlayerController.DigUpTile`은 타일 제거를 타일 버퍼에 넣고 **아이템 드롭은 별도 커맨드 버퍼에**
넣는다. 우리가 지울 수 있는 것은 앞의 것뿐이라 막으면 **바닥은 남고 아이템은 떨어진다** — 무한
반복 가능한 자원 복제이고, 아래 §"절대 발생해서는 안 되는 것"을 정면으로 위반한다. 구덩이 하나보다
훨씬 나쁘다. 근원에서 막는 길(`TileType.immune`)은 세이브에 흔적을 남겨 별도 결정이 필요하다 —
`research.md` 21-5.

### 보호 대상

**고정된 것은 보호하고, 소모되는 것은 보호하지 않는다.**

여기서 "고정된 것"이란 그 자리에 계속 있으라고 놓인 것을 말한다. 상자, 작업대, 벽처럼 사라지는 것이 전제되지 않은 것들이다. 반대로 작물이나 광석 덩어리는 캐고 수확해서 없애는 것이 원래 용도다.

헷갈릴 때는 **부쉈을 때 그 물건이 그대로 돌아오는가**로 판단한다. 상자를 부수면 상자가 돌아온다. 작물을 수확하면 작물이 아니라 열매가 나온다.

**보호한다**

- 플레이어가 설치한 구조물 — 상자, 작업대, 드릴, 로봇 팔, 컨베이어, 전선, 문, 함정, 조명, 가구
- 장식용 화분·나무처럼 부수면 그 물건이 그대로 돌아오는 것
- 지형에 고정된 것 — 벽, 바위, 지형에 박힌 광석
- 바닥 타일과 **벽** _(2026-08-07 포함으로 확정 — 아래 결정 기록)_

> **바닥과 벽을 보호 대상에 넣은 이유 (결정 기록, 2026-08-07)**
>
> **인게임에서 사용자가 지적했다.** 파일런을 켠 범위 안에서 상자와 작업대는 살아남는데 바닥과
> 벽은 그대로 부서졌다. 기지를 지키는 물건이 기지의 **벽**을 안 지키는 것은 앞뒤가 안 맞는다.
>
> 원래 뺀 이유는 **자원 복제 위험**이었고, 그 걱정은 대상을 잘못 겨눴다. 벽의 전리품은 **파괴
> 시점**에 나온다(`object_flags.csv`: 벽 41종 전부 `lootTable=1`·`lootOnDmg=0`). 파괴를 막으면
> 전리품이 아예 안 나오므로 복제가 **구조적으로 불가능**하다. 복제는 "안 죽으면서 계속 뱉는" 것이
> 라야 성립하고, 그건 광석·드릴 대상·`DropsLootWhenDamagedCD`의 성질이다 — **그 넷은 계속 제외**한다.
>
> 기술적으로도 성립한다. 타일 채굴은 `IndestructibleCD`를 보지 않지만(`research.md` 20장),
> 설치물과 **같은 파괴 관문**을 지나므로 `DontDestroyOnZeroHealthCD`로 막힌다.
>
> **감수하는 것**: 이 모드가 처음으로 **플레이어가 만들지 않은 것**을 보호한다. 파일런을 켠 채로는
> 범위 안에서 굴을 팔 수 없다. §6의 "기지를 수정하려면 파일런을 끄면 된다"가 그대로 답이 된다.

**보호하지 않는다**

- **광석 덩어리** (드릴로 캐서 고갈시키는 것)
- 소모·수확 대상 — 작물, 수확용으로 심은 나무, 알·둥지 등 채집물
- 몹, 플레이어, 떨어진 아이템

설치물이 여러 타일을 차지하는 경우, **모든 타일이 범위 안에 들어와야 보호된다.** 한 칸이라도 밖으로 나가면 보호되지 않는다. 판정이 단순하고, 사용자도 "완전히 넣어야 한다"로 이해하기 쉽다.

파일런 개수에는 제한을 두지 않는다.

보호가 켜져 있으면 범위 안에서 곡괭이질도 통하지 않는다. 기지를 넓히려면 파일런을 꺼야 한다. 반면 농사와 드릴 자동화는 켜둔 채로도 정상적으로 돌아간다.

> **작물을 제외한 이유 (결정 기록)**
>
> 기지 개조는 가끔 하는 일이지만 수확과 자원 채취는 상시로 돌아가는 일이다. 작물과 광석 덩어리까지 잠그면 수확할 때마다, 드릴을 돌릴 때마다 파일런을 껐다 켜야 해서, 결국 사용자가 파일런을 꺼놓게 된다. 특히 드릴 자동화가 멈추는 것은 치명적이다.
>
> 또한 폭발물을 터뜨려 작물을 한 번에 수확하는 플레이를 막지 않기 위해서이기도 하다. 이 경우 폭발이 구조물에는 통하지 않고 작물만 정리된다.
>
> 그 대가로, 기지에서 실수로 폭발이 일어나면 **작물과 광석 덩어리는 함께 사라진다.** 이는 의도된 결과로 감수한다. 이 모드가 지키려는 것은 상자와 설비이지 밭이 아니다.

### 절대 발생해서는 안 되는 것

**자원이 무한히 생성되어서는 안 된다.**

특히 드릴이 광석 덩어리를 캐는 경우가 위험하다. 드릴은 보호 대상이지만 광석 덩어리는 아니다. 만약 구현이 이 둘을 구분하지 못해 덩어리까지 보호해버리면, 덩어리가 고갈되지 않아 **광석이 무한정 나온다.**

자원 복제는 세이브 경제를 되돌릴 수 없이 망가뜨리고, 멀티플레이 서버에서는 더 심각하다. 다른 어떤 기능보다 우선해서 검증한다.

### 파일런 자신

**켜져 있는 동안 파일런은 무적이다.** 폭발로도, 곡괭이로도, 몹 공격으로도 파괴되지 않는다.

파일런이 먼저 부서지면 그 순간 기지 전체가 무방비가 되기 때문이다. 회수하려면 먼저 꺼야 한다.

### 파일런이 여러 개일 때

범위가 겹쳐도 문제없다. **어느 하나의 켜진 파일런 범위 안에 있으면 보호된다.**

## 7. 시각·청각 표현

### 상태 표시

| 상태 | 외형                                         |
| ---- | -------------------------------------------- |
| 꺼짐 | 발광 부위가 어둡게 죽어 있음                 |
| 켜짐 | 발광 부위가 밝게 빛나고, 주변에 옅은 빛 번짐 |

스프라이트는 **한 종류만 만들고 발광 레이어를 켜고 끄는 방식**으로 처리한다. 이렇게 하면 두 상태의 실루엣이 완전히 동일해 전환 시 튀지 않는다.

게임의 전기 기계들이 전력이 들어오면 바닥 홈이 노랗게 빛나는 것과 같은 시각 문법을 따른다. 플레이어가 설명 없이도 "작동 중"을 읽어낼 수 있다.

### 활성화 순간 이펙트

한 번 보고 넘어가는 짧은 연출. 과하지 않게.

- 파일런 주변에서 **짧게 터지는 빛**
- 지속 시간 1초 이내
- 비활성화 시에는 빛이 잦아들며 꺼지는 역방향 연출

**파동이 보호 범위 경계까지 퍼지게 하지 않는다.** 그렇게 하면 껐다 켜는 것만으로 범위를 알 수 있어 렌즈의 존재 이유가 사라진다. 이펙트는 "상태가 바뀌었다"만 알리고, 범위는 알리지 않는다.

### 보호 범위 표시

두 가지가 충돌한다. 범위를 모르면 경계 바로 바깥에서 폭발시켰다가 또 기지를 날린다. 그렇다고 상시 표시하면 기지 바닥이 덮여 미관을 해친다.

해법은 **범위를 보는 수단을 하나로 못 박는 것**이다.

| 상황                      | 표시                           |
| ------------------------- | ------------------------------ |
| **렌즈를 손에 들었을 때** | **화면 안 모든 파일런의 범위** |
| 그 외 모든 상황           | 표시하지 않음                  |

커서를 올려도, 파일런을 손에 들어도, 파일런을 켜고 꺼도 범위는 보이지 않는다. 오직 렌즈뿐이다.

이렇게 하면 평소 화면이 완전히 깨끗하고, 렌즈가 확실한 존재 이유를 갖는다. 범위 표시가 여기저기 흩어져 있으면 렌즈는 만들 이유가 없는 장식품이 된다.

렌즈를 아직 만들지 않은 사용자는 범위를 눈으로 볼 수 없다. 이는 의도된 것이다. 파일런 설명문에 렌즈의 존재를 안내하고, 그 전까지는 대략적인 감으로 사용하게 한다.

**게임에 이미 있는 범위 표시 방식을 그대로 따른다.** 아이템 수집기처럼 범위를 가진 기존 설치물이 어떤 표현을 쓰는지 조사해 재사용하고, 새로 만들지 않는다.

이유는 넷이다. 사용자가 이미 아는 시각 언어라 학습이 필요 없고, 게임과 톤이 완전히 일치해 미관 문제가 없으며, 이미 최적화된 방식이라 성능 부담이 없고, 새로 만들 것이 없다.

재사용이 불가능한 경우에만 대안을 찾는다. 그때도 **바닥 텍스처를 덮지 않는 쪽을 우선한다.** 경계 전체를 칠하는 것보다 모서리 표식이나 아주 옅은 윤곽이 낫다. 기지를 공들여 꾸민 사용자일수록 이 모드가 필요한데, 표시 때문에 기지가 이상해 보이면 그 자리에서 모드를 지운다.

### 사운드

- 켜질 때 / 꺼질 때 각각 짧은 효과음
- 보호가 실제로 피해를 막아냈을 때 짧은 피드백음 — _선택 사항이지만 있으면 신뢰감이 크게 오른다_
- 가능하면 게임 내 기존 효과음을 재사용

## 8. 멀티플레이

- 파괴 판정과 토글 상태는 **서버가 결정한다.** 클라이언트가 임의로 판단하지 않는다.
- 모든 플레이어에게 동일하게 적용된다. 설치한 사람만 보호받는 식의 소유권 개념은 두지 않는다.
- 배포 시 서버 측 모드로 표기한다.

## 9. 성능 요구사항

모드를 설치한 상태와 설치하지 않은 상태의 **체감 차이가 없어야 한다.** 대형 기지, 자동화 설비가 빽빽한 구역, 다인 멀티플레이에서도 마찬가지다.

### 지켜야 할 것

**상태 갱신은 사건이 있을 때만 한다**
매 프레임 월드를 훑어 "이 물건이 보호 범위 안인가"를 계산하지 않는다. 갱신이 필요한 순간은 정해져 있다 — 파일런이 켜지거나 꺼질 때, 파일런이 설치되거나 제거될 때, 범위 안에 물건이 새로 놓이거나 사라질 때. 그 외에는 아무 일도 하지 않는다.

**판정은 거리 계산이 아니라 표식으로 한다**
피해가 발생할 때마다 모든 파일런과의 거리를 재는 대신, 보호 상태가 바뀌는 시점에 대상 오브젝트에 표식을 붙여둔다. 이후 판정은 "표식이 있는가"를 한 번 조회하는 것으로 끝난다. ECS는 이런 방식에 최적화되어 있다.

**Burst 해제는 최후의 수단이다**
Burst로 컴파일된 시스템의 Burst를 끄면 그 시스템 전체가 네이티브 코드에서 관리 코드로 떨어진다. 피해 처리처럼 자주 도는 시스템이라면 그것만으로 렉의 원인이 된다. Burst를 유지한 채 함수 포인터만 교체하는 방법을 우선 검토하고, 해제는 다른 수가 없을 때만 선택한다.

**자주 도는 경로에서 메모리를 할당하지 않는다**
피해 판정처럼 초당 수백 번 호출될 수 있는 지점에서는 리스트 생성, LINQ, 문자열 조작을 하지 않는다.

**시각 효과는 클라이언트에서만 처리한다**
발광, 활성화 파동, 범위 표시는 화면에만 존재하면 되므로 서버 시뮬레이션에 올리지 않는다. 특히 **범위 표시를 타일마다 오브젝트를 생성해 구현하지 않는다.** 21×21이면 경계만 해도 80칸이다.

**깜빡임이 없어야 한다**
파괴되는 모습이 잠깐 보였다가 되돌아오는 현상은 없어야 한다. 사용자 눈에는 그것도 버그로 보이고, 멀티플레이에서 특히 드러나기 쉽다.

"피해를 받았지만 무효화한다"보다 **"애초에 유효한 피해가 아니다"** 쪽이 이 문제에서 유리할 수 있다. 채굴 등급이 모자라면 벽이 아예 깨지지 않는 것과 같은 원리다. 다만 실제 코드 구조를 확인하기 전에는 어느 방식이 가능한지 알 수 없으므로, **방식은 열어두고 여러 방향으로 검토한다.**

**되돌릴 수 있는 방식이어야 한다**
오브젝트의 원래 값을 덮어썼다가 보호를 풀 때 정확히 복원하지 못하면, 그 물건은 영구히 망가진 채 세이브에 남는다. 어떤 방식을 택하든 이 조건은 만족해야 한다.

**네트워크로는 파일런 정보만 오간다**
동기화 대상은 파일런의 위치와 켜짐/꺼짐 상태뿐이다. 보호 대상 목록이나 타일 정보를 주고받지 않는다.

### 확인 방법

1단계 검증 때 함께 측정한다. 기지 규모를 키운 상태에서 모드를 켜고 끄며 비교하고, 특히 **폭발이 여러 오브젝트에 동시에 닿는 순간** 끊김이 없는지 본다. 자동화 설비가 밀집한 구역에서도 확인한다.

수치 목표를 세우기보다 "모드를 껐다 켰을 때 차이를 느낄 수 없어야 한다"를 기준으로 삼는다.

### CoreLib 사용 여부

**공식 SDK만으로 먼저 시도한다.** 막히는 지점이 있으면 그때 CoreLib 도입을 검토한다.

CoreLib는 BepInEx 시절의 빈틈을 메우려고 만들어졌는데, 현재는 공식 SDK가 커스텀 오브젝트 추가를 직접 지원한다. 반면 도입하면 배포가 복잡해진다. 의존하는 모듈 전부와 CoreLib 루트를 직접 의존성으로 명시해야 하고, 게임의 mod.io 연동이 전이 의존성을 제대로 처리하지 못하기 때문이다. 사용자가 하나라도 빠뜨리면 작동하지 않는다.

의존성이 늘면 그 라이브러리가 게임 업데이트를 따라오지 못할 때 이 모드도 함께 멈춘다. 추가할 오브젝트가 네 개뿐이라 규모도 작다.

## 13. 개발 순서

각 단계는 **게임에서 실제로 확인한 뒤** 다음으로 넘어간다.

**1단계 — 피해 차단 검증**
설정도 아이템도 없이, 하드코딩으로 "모든 설치물이 파괴되지 않음"을 구현한다. 게임에서 폭발을 터뜨려 상자가 살아남는지, 곡괭이로도 철거되지 않는지 확인한다.

_이 단계에서 아래를 반드시 함께 확인한다._

- 설치물과 자연 지형이 코드상 구분되는가
- **드릴을 광석 덩어리에 붙여놓고 방치했을 때 덩어리가 정상적으로 고갈되는가** — 고갈되지 않으면 자원 복제 버그다
- 작물이 정상적으로 수확되는가
- 바닥 타일이 설치물과 같은 경로로 처리되는가
- 패치한 시스템이 Burst 컴파일 대상인가, 그렇다면 Burst를 유지한 채 후킹할 수 있는가
- **설치물의 파괴가 어떤 구조로 되어 있는가** — 채굴 등급 같은 조건으로 막히는지, 체력만 깎이는지, 또는 다른 방식인지
- 멀티플레이에서 파괴가 잠깐 보였다가 되돌아오는 현상이 있는가
- 기지가 큰 상태에서 모드를 켜고 껐을 때 프레임 차이가 느껴지는가

**2단계 — 좌표 조건**
특정 좌표 반경 안에서만 보호되도록 조건을 추가한다.

**3단계 — 커스텀 오브젝트**
파일런 설치물을 추가하고, 그 좌표를 2단계에 공급한다. 임시 스프라이트를 사용한다.

**4단계 — 토글과 상태 저장**
상호작용 토글, 세이브 유지, 파일런 자체 무적화.

**5단계 — 시각 표현**
발광 레이어, 활성화 파동, 커서를 올렸을 때의 범위 표시, 사운드.

**6단계 — 부가 요소**
전용 작업대를 추가하고 파일런 레시피를 옮긴다. 렌즈와 리모콘을 추가한다. 렌즈의 범위 표시와 리모콘의 원격 토글을 구현한다.

**7단계 — 아트 마감과 배포**
최종 스프라이트, 설정 파일, mod.io 및 Steam Workshop 업로드.

**작은 아이콘 (2026-09-14 확정)** — 인벤토리 칸 밖에서 아이템을 보여줄 때 쓰는 10×10 그림이다.
바닥에 떨어졌을 때, 설치물을 손에 들었을 때, 제작 재료 목록이 여기에 해당한다. 인벤토리 아이콘(16×16)을
그대로 쓰면 바닐라 옆에서 너무 크게 떠서 따로 그린다(테스터 지적). "손에 들었을 때의 스프라이트"라는 미정
항목이 이것으로 풀렸다. 규격은 `research.md` 30장.

초안 스프라이트는 이미 제작되어 있다. 게임의 실제 규격과 팔레트가 확인되면 그에 맞춰 다시 뽑는다. 스프라이트는 절차적 생성 스크립트로 만들어져 있어, 색상 상수와 좌표만 바꾸면 재생성된다.

### 기술적으로 확인된 사항

- Burst 컴파일된 시스템은 SDK가 제공하는 `BurstDisabler` API로 선택적으로 Burst를 끈 뒤 Harmony로 패치할 수 있다. Burst를 끄지 않고 함수 포인터만 교체하는 방법도 공식 예제로 제공된다.
- Harmony는 게임에 기본 포함되어 있으며, `[HarmonyPatch]` 어노테이션이 붙은 클래스는 자동 적용된다.
- 서버 전용 시스템은 `WorldSystemFilterFlags.ServerSimulation` 지정과 `PugSimulationSystemBase` 상속으로 작성한다.
- 오브젝트 종류 판별에는 `ObjectDataCD`, 위치에는 `LocalTransform`, 플레이어 식별에는 `PlayerGhost` 컴포넌트를 사용한다.
